# kvstore performance benchmark

Generated by `python3 bench/gen_bench.py` (run from `problems/kvstore/`; fixed seeds). Expected outputs come from the Python reference, driven in process the same way `gen_tests.py` drives it. Run with `python3 run_tests.py kvstore --tests-dir problems/kvstore/bench -- <impl>/run.sh`.

- `001_bulk_ingest`: an empty store loaded with 22,000 user records (inline objects of about 150 bytes; 1.5% carry a 0.2-5 KB `bio` that spills to overflow pages). Keys arrive in random order, mostly in explicit transactions of 125-375 puts, with some short runs of implicit commits. Read-back `get`s and short `scan`s are mixed in, then 40 batches replace existing records. This measures raw write throughput: B+tree inserts and splits, page encoding, WAL appends with CRC, automatic checkpoints, and writing an 8 MB `main.tdb`.
- `002_index_queries`: starts from a checkpointed 12,000-record store (input `main.tdb`). It builds four secondary indexes (`city`, `age`, `score`, `addr.zip`) and then runs about 1,800 mixed operations. Of these, 40% are `find`s: mostly index plans with equality or one-sided range candidates, about 13% scan plans (`or`, unindexed fields). The rest are updates of indexed fields, short range deletes in transactions (these drive borrow and merge in the primary and index trees), inserts, `unset`s, `get`s and `scan`s, plus one drop and rebuild of an index. This is the algorithmically heaviest part of the program: index maintenance, candidate range walks with primary lookups, predicate evaluation and sorting by primary key.
- `003_mixed_recovery`: the random mixed workload from `gen_tests.py` (`gen_workload`, the same operation mix as the public `random_*` tests) at a larger scale: 25,000 commands over a 6,000-key space. It starts from a database and a write-ahead log that is cut three-quarters of the way through. The cut log holds about 187 KB of commits made after the last checkpoint, so opening the store means recovering and trimming the log. The script exercises everything at once: puts of scalars, objects, lists and overflow strings; deletes, updates, `unset`s, transactions and rollbacks; checkpoints; unindexed `find`s (which walk the whole store); and `scan`s. Some of its `create index` commands fail with `index-key-too-long` by design, so indexes play only a small part here. `002` covers them.

## Long tier

`python3 bench/gen_bench.py --long [001] [002] [003]` (from `problems/kvstore/`) writes `../bench-long/` (about 25 minutes per full run; expected outputs from the reference, peak reference RSS 380 MB). No SPEC.md limit needed changing.

- `001_bulk_ingest`: 44,000 users (was 22,000) loaded the same way, then 2,800 batches of record replacements (was 40): about 610k `put`s. Ingest is write-bound, so this input is mostly data (91 MB of commands).
- `002_index_queries`: a 40,000-record store (was 12,000) with 5,200 mixed operations (was 1,800) in the same proportions, so the deleted fraction stays similar and every `find` walks proportionally larger candidate ranges.
- `003_mixed_recovery`: the same recovery start, then 170,000 commands of the random mixed workload (was 25,000) over the same 6,000-key space.

Measured on a loaded machine (best of two, wall): 001 6.2 s (Go; Rust 10.2 s), 002 7.2 s (Go; C++ 9.3 s), 003 7.3 s (Go; C++ 8.6 s). Peak RSS at most 270 MB (Go, 001). bench-long is about 174 MB, most of it 001's commands and database.

The Python implementation passes all three: 192 s, 195 s and 166 s, peak RSS at most 322 MB.
