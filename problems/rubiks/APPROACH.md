# rubiks: implementation approach

SPEC.md defines what the solver does. This note fixes how it is done. Where the
two seem to conflict, SPEC.md wins.

Sizes used below: `N` scrambles (at most 100), `T` tokens in a scramble (at
most 1000). Everything else is a constant of the cube group; the cost that
dominates is the one-time build of four distance tables, which is the same for
every input.

## Overall approach

Thistlethwaite's four-phase algorithm with a precomputed exact distance table
per phase and greedy descent. The cube is held at cubie level (corner and edge
permutation and orientation). Each phase has a coordinate: a small integer
that identifies the cube's coset of the next subgroup. At start-up, for each
phase, small per-component move tables are built and a breadth-first search
from the goal coordinate fills a byte array with the exact distance of every
coordinate value. Solving a scramble applies its tokens to a solved cube, then
for each phase repeatedly takes the first allowed move that lowers the table
distance by one until it reaches zero. The phase lengths are optimal, so the
solution has at most 7 + 10 + 13 + 15 = 45 moves. Output is collected in one
buffer and written once.

## Required choices

1. **Cubie representation.** A state is four small arrays: corner permutation
   and orientation (8 each, orientation mod 3) and edge permutation and
   orientation (12 each, mod 2). The 18 moves are themselves such states,
   derived once at start-up from the facelet cycles in SPEC.md (or written as
   constants that equal them). Applying a move is one 20-element composition.
   Edge orientation is referenced so that only F and B quarter turns flip
   edges, and corner orientation to the U/D facelet, so that the phase goals
   below are "coordinate = goal value". Do not simulate 54 facelets during
   search or table building.
2. **Phase move sets.** Phase 1: all 18 moves. Phase 2: no F/B quarter turns
   (14 moves). Phase 3: U/D any turn plus L2 R2 F2 B2 (10 moves). Phase 4:
   the six half turns. Each set is closed under inverses, so distance from the
   goal equals distance to it.
3. **Phase coordinates and table sizes (exactly these spaces).**
   - Phase 1: orientation of 11 edges (the twelfth is implied): 2,048 values.
   - Phase 2: orientation of 7 corners (3⁷ = 2,187) times the set of positions
     holding the four E-slice edges (C(12,4) = 495): 1,082,565 values.
   - Phase 3: the class of the corner permutation modulo the 96 corner
     permutations generated by half turns (8!/96 = 420 classes) times the set
     of the eight U/D-layer positions holding M-slice edges (C(8,4) = 70):
     29,400 values. The class is taken on the side that moves do not act on
     (relabelling of pieces by the 96-element group), so it transforms
     consistently under moves; the goal is the identity's class with the
     M-slice edges in M-slice positions.
   - Phase 4: index of the corner permutation among the 96 half-turn corner
     permutations, times the permutation of each of the three edge slices
     within its own four positions (24³): 1,327,104 values (663,552
     reachable).
   Permutations of up to 8 elements are ranked with the Lehmer code;
   k-subsets either with the combinatorial number system or a 2¹²/2⁸-entry
   mask-to-rank lookup. The corner coordinates go through two 8!-entry
   lookups indexed by Lehmer rank, filled once: the 96 half-turn corner
   permutations are the closure of the identity under the six half turns
   (rank → index 0..95), and the classes are labelled by taking each still
   unlabelled permutation in rank order and marking its 96 relabellings with
   a new class number, 40,320 compositions in all (rank → class 0..419, one
   representative kept per class). Each phase's BFS starts from the single
   goal coordinate.
4. **Per-component move tables, then BFS on coordinates.** For each component
   of a coordinate (edge flip, corner twist, slice set, corner class, U/D
   split, half-turn corner index, slice permutation) build a table
   `component value × phase move → component value` by decoding each value
   into a representative, applying the move once, and re-encoding. The
   corner-class table is built from one representative permutation per class
   (420 × 10 entries), not from all 8! permutations. The BFS then computes a
   successor purely as table lookups combined arithmetically (e.g.
   `twist' × 495 + slice'`); it never builds a cube state or calls a ranking
   function per edge of the search.
5. **Distance tables are flat byte arrays filled by plain BFS.** One unsigned
   byte per coordinate value, initialised to an "unvisited" sentinel, with a
   preallocated integer FIFO queue (or per-depth frontier arrays). No hash
   maps, no per-node objects. Total work is O(Σ table size × moves), about
   15.2 million transitions for phase 2 and well under that for the others.
6. **Tables are built once per process.** All four tables are built at
   start-up (or lazily on first use) and shared by all scrambles; no search
   state is rebuilt per scramble.
7. **Solving is greedy descent, O(phase length × moves) per phase.** From the
   current state, try the phase's moves in a fixed order and take the first
   whose successor has distance exactly one less; repeat until distance 0.
   The successor may be evaluated either by applying the move to the cube and
   recomputing the coordinate or by the move tables; there is no search per
   scramble beyond this descent.
8. **Input.** Read all of standard input at once, split on `\n` following the
   SPEC rules for the final newline, and map each token to a move index in
   O(1) (its face letter plus an optional `2` or `'` suffix, or a small
   lookup table). Apply each token to the cube with one composition: O(T) per
   scramble.
9. **Output.** Append each solution's tokens, separated by single spaces and
   terminated by `\n`, to one growable buffer; write it to standard output
   once at the end.

## Left to the implementer

- Container types, struct layout, integer widths of move tables, naming and
  module structure.
- Whether the BFS uses one FIFO queue or level-by-level frontiers, and
  whether transitions are inlined or factored into a helper.
- The order of the coordinate's components and of the move list, and the
  exact ranking functions, as long as each table has the size given above.
- Whether descent applies moves to the cube or follows the move tables.
- Whether adjacent same-face moves across phase boundaries are merged (the
  bound of 45 already satisfies SPEC.md's 52).
- Eager or lazy table construction, and deriving the move cubies at start-up
  versus writing them as constants.
- Micro-optimisations such as packing two distances per byte, provided the
  same tables and BFS are used.

## Pitfalls

- Using the full corner permutation (8! = 40,320) in the phase 3 coordinate
  instead of its 420 half-turn classes: the table grows from 29,400 to
  2,822,400 entries, and its BFS (about 28 million transitions) costs nearly
  twice the phase 2 BFS that otherwise dominates start-up.
- Encoding phase 4 as five independent permutations of four (two corner
  tetrads plus three edge slices, 24⁵ = 7,962,624 entries) instead of the 96
  reachable corner permutations times 24³: six times the memory to allocate
  and initialise for the same 663,552 reachable states.
- Building a move table for all 40,320 corner permutations (unrank, compose,
  re-rank for every one) when only 420 class representatives or 96 half-turn
  permutations are needed.
- Generating BFS successors by composing whole cube states and recomputing
  coordinates (with ranking) for every edge, instead of component move-table
  lookups.
- Bidirectional or iterative-deepening search per scramble with hash-map
  visited sets: correct but orders of magnitude slower than table descent.
- Calling an indirect function (a closure or function pointer passed to a
  generic BFS) and splitting the coordinate with a chain of divisions on every
  BFS edge in a language whose compiler does not inline it; keep the hot
  transition loop direct.
- Matching each input token by comparing it against all 18 move names, or
  writing each output token with a separate unbuffered write.
