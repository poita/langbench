# cardgame performance benchmark

Generated by `gen_bench.py` (fixed seeds); expected outputs come from the Python reference (`reference/main.py`, 9-22 s per input). Every script is self-played through the reference engine's own `LEGAL` output, so actions are real, accepted moves on the main card database (plus ~0.2-1% deliberately rejected lines). The inputs stay within all SPEC limits (Spire <= 1000000, entry counts <= 1000, TURNLIMIT 100000). Inspection directives are only issued outside combat.

- `001_long_match_throughput`: one long match, two 8000-card decks drawn from the full card pool, Spire 400000, 45000 script lines (~390 turns). The board grows and gets wiped as it would in real play (a few dozen to ~450 objects), so this measures sustained throughput across the whole engine: chain and priority, triggers, combat, draws, and event output. It is a fair test because it is ordinary play at scale, with no degenerate loops.
- `002_aura_trigger_board`: both players start with 14 aura/trigger permanents, cap 4 and MAXCAP 14, and decks weighted toward aura and trigger cards. The self-play prefers playing those cards and rarely attacks, so the Field fills with hundreds of objects whose characteristics depend on many stacked layer-2/3/4 statics and conditional auras, and every event fans out to many listeners. This is the algorithmically hardest part of the program (layer derivation plus trigger collection over a big board), which SPEC section 2 names as the performance trap. It comes from realistic deck archetypes, not from one pathological card.
- `003_mixed_trace_session`: a two-house-vs-two-house match (3000-card decks) run as an interactive session. `TRACE legal` prints the legal-action list after every accepted action, about 1% of lines are rejected with `ERR`, and about 1% are `DUMP`, `LEGAL` and `CARD` directives (15000 script lines in all). It weights the legal-action enumerator (target-tuple generation and ordering), error handling and the output formatter, together with normal rules processing.

Agreement: the C++, Go, D and Python implementations under `runs-large/` match the expected output on all three inputs, and so does Rust on 001 and 002. Rust fails 003 because it lists `(chained)` target candidates in Chain-stack order and not by ascending cid, which SPEC 12.4 requires (6 `PLAY ... ~cid` lines in `LEGAL` blocks). If DUMP directives were issued during combat, the C++, Rust, Go and Python versions would also show a destroyed attacker's blockers as still `blocking`, against SPEC 7.5. That is the same bug that fails hidden tests 373 and 401, and it is why the generator keeps directives out of combat.

## Long tier

`python3 bench/gen_bench.py --long [name...]` writes `bench-long/` with the same three self-played matches (same
seeds, card mixes and driver settings), played for more script lines with more Spire and bigger decks so the match
keeps going (`LONG_ARGS`):

- 001: 135,000 lines (3x), Spire 1,000,000, 16,000-card decks. The longer match builds a much bigger board, so the
  work grows faster than the line count.
- 002: 110,000 lines (~8x), Spire 1,000,000, 16,000-card decks.
- 003: 45,000 lines (3x), Spire 60,000, 9,000-card decks.

No SPEC.md limit changes (Spire 1,000,000 and TURNLIMIT 100,000 are within the stated ranges). Expected outputs come
from `reference/main.py`. The self-play driver enumerates LEGAL through the Python engine before every action, so
generation is slow: about 2 h 20 min for 001, 55 min for 002 and 12 min for 003.

Times are user CPU, best of 2, measured at load average ~10-17 on 8 cores. Python times come from a more loaded run:

| input | fastest (user s) | others (user s) | peak RSS compiled | python (wall / user, RSS) | size |
| --- | --- | --- | --- | --- | --- |
| 001_long_match_throughput | cpp 9.6 | go 11.5, rust 13.9, d 33.2 (fails) | 256 MB | 640 s / 390 s, 331 MB | 60 MB |
| 002_aura_trigger_board | cpp 5.9 | go 6.2, rust 7.0, d 14.6 (fails) | 71 MB | 258 s / 225 s, 93 MB | 12 MB |
| 003_mixed_trace_session | go 0.52 | cpp 0.58, rust 0.65, d 1.27 | 214 MB | 17 s / 15 s, 409 MB | 62 MB |

`bench-long/` is 129 MB. 003 does not reach 5 s: `TRACE legal` prints the legal-action list after every action,
so its output grows with the board (62 MB at 3x) and reaching 6 s would need ~400 MB of expected output.

C++, Rust, Go and Python pass all three. D fails 001 and 002. Both divergences are `COUNTERS` lines from
`(on ally-arrive (counters 1 it))` (Soil Tender) when one Grave Tide reanimates many units at once: the same ability of
the same source triggers several times in one batch, so those triggers have identical trigger keys (SPEC 13.3), and D
orders them differently from the collection order the other four keep (so each trigger's `it` lands on a different
unit). SPEC 13.3 says the batch is "sorted by ascending trigger key" but does not say how identical keys are ordered;
the short tier never hits this case.

Decision (equal trigger keys): SPEC 13.3 now says that triggers with equal keys keep the order in which they were
collected. That is what the reference does (Python's stable `list.sort` over the pending list in collection order),
and the order is well defined: equal keys only arise when one ability of one source triggers on several events,
events occur one at a time in an order the spec fixes (here the canonical order of 6.9 `each`), and each event
collects at most once per ability. The D implementation's unstable `std.algorithm.sort` in `pushTriggers` is
therefore a D bug. No expected output changed. The Python implementation needs more than 10 minutes of wall time on 001 on this
loaded machine (390 s of CPU).
