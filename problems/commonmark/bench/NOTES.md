# commonmark benchmark inputs

Generated by `gen_bench.py` (fixed seeds). Expected outputs come from
`reference/main.py` and are cross-checked byte-for-byte against `cmark` 0.31.2,
the oracle of this problem. Every input passes the SPEC subset checks
(`gen_tests.subset_violation`) and stays within SPEC's 1 MB input limit. Because
of that limit, the fastest compiled implementations take only about 30-40 ms per
input (process start-up is a few ms of that). A whole document is one stdin
stream, so the work cannot be spread over several documents.

- `001_docs_site` (990 KB): a realistic documentation site with chapters,
  headings, wrapped prose with light inline markup, nested bullet and ordered
  lists (tight and loose), fenced and indented code, block-quoted notes and
  thematic breaks. It measures overall block-parsing and HTML-rendering
  throughput on the kind of input a Markdown converter usually gets.
- `002_inline_dense` (997 KB): long prose paragraphs (150 to 900 tokens each) that
  are dense with nested emphasis, intraword `_`/`*`, links and images with
  nested content and every title and destination form, code spans with
  several backtick lengths, autolinks, entities, escapes, hard breaks, and a
  few unmatched delimiters and brackets. It stresses the hardest part of the
  program: the delimiter and bracket stacks, process-emphasis and the code-span
  search over large paragraphs. It does this without degenerate runs.
- `003_mixed_random` (990 KB): a random document from the test suite's
  `gen_document` generator (seed 3005) that mixes every construct in the
  subset, including edge cases: lazy continuation, list-type changes, setext
  headings, odd fences, tabs, nested quotes/lists up to depth 4 and invalid
  links. It measures a broad, correctness-heavy mixed workload.

## Long tier

`python3 gen_bench.py --long` writes `../bench-long/` (same names; expected outputs from
`reference/main.py`, cross-checked byte for byte against cmark 0.31.2; every input passes
the subset checks). SPEC.md's input limit is raised from 1 MB to 16 MB for this tier.

- `001_docs_site`: the same documentation-site generator run to 15.9 MB.
- `002_inline_dense`: the same inline-dense generator run to 15.9 MB.
- `003_mixed_random`: consecutive whole `gen_document` documents (seeds 3005, 3006, ...,
  skipping any that leave the subset) joined to 15.9 MB. A single 16 MB `gen_document`
  always contains an out-of-subset `<`, hence the concatenation.

This problem is bound by its input size: a whole input is one document, and the
compiled builds convert about 150 MB/s, so 5 s would need roughly 750 MB of Markdown
per input (far over the size budget, with RSS of several GB). The long tier therefore
does **not** reach the 5 s target: the fastest build takes about 0.1 s on each input
(C++/Rust 0.08-0.11 s, Go/D 0.10-0.16 s, CPU seconds normalised to a lightly loaded
machine). Peak RSS at most 251 MB (Go). Size on disk 101 MB.
