# minisql performance benchmark

Generated by `gen_bench.py` (fixed seeds); expected outputs come from `reference/main.py` (about 75 s for all three) and also match SQLite through `gen_tests.py`'s oracle. Every table stays at or below the spec's 20 000 rows and is loaded with 500-row `INSERT` statements. The load comes from running many statements over those tables.

- **001_scan_filter_group**: loads 2 000 users, 500 products and 20 000 orders (~1 MB of SQL), then runs ~420 single-table queries: filters with LIKE, arithmetic, NOT and NULL tests; GROUP BY with up to ~2 000 groups and HAVING; ORDER BY over the whole table with LIMIT/OFFSET; and an UPDATE every 30 statements. It ends with an unlimited 20 000-row sort. This tests parsing throughput, the expression evaluator, sorting and grouping, all of which are paths every query uses.
- **002_equi_joins**: the same schema plus ~150 joins on equality conditions: orders-users, orders-products, and self joins of users (city/age) and orders (user_id, amount). These include extra residual predicates, GROUP BY over join results and LIMITed ordered outputs. The last query is an unordered join whose output depends on nested-loop order. This is the hardest part of the spec. A hash/sort join is needed, but each join produces only 10^4–10^5 pairs, so the test measures join quality rather than one degenerate blow-up.
- **003_mixed_oltp**: an OLTP-style session of 4 500 statements on a 19 000-order base. It mixes point lookups by id and user_id, 1–3-row INSERTs, point UPDATEs/DELETEs, small per-user joins and ~2% erroneous statements, with an aggregate or join report every 150 statements. With no indexes, every point statement is a full scan, so this measures per-statement overhead plus scan speed under constant mutation, which is how the engine is used in practice.

## Long tier

`python3 gen_bench.py --long` writes `../bench-long/` (same names; expected outputs from
`reference/main.py`, about 42 minutes for all three). The tables and their loading are
unchanged; only the statement count grows, so the inputs stay small (12 MB in total
with outputs).

- **001_scan_filter_group**: 7,600 single-table queries instead of 420 (18x), same mix,
  with an UPDATE every 30 statements and the final full sort.
- **002_equi_joins**: 6,400 joins instead of 150 (43x), same templates.
- **003_mixed_oltp**: an OLTP session of 36,000 statements instead of 4,500 (8x), same
  weights and a report every 150 statements. Because the session keeps inserting, the
  orders table grows from 19,000 to about 27,000 rows by the end; SPEC.md's Performance
  section now says so.

Measured on a heavily shared machine; times are CPU seconds normalised by a calibration
run to a lightly loaded machine: fastest per input 001 Rust 6.4 s, 002 Rust 7.2 s,
003 C++ 6.6 s (Go and D are slower on all three). Peak RSS of the compiled builds at
most about 110 MB.
