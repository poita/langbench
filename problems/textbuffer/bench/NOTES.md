# textbuffer performance benchmark

Regenerate with `python3 problems/textbuffer/bench/gen_bench.py` (fixed seeds, about a minute). Commands are chosen against a live reference `Buffer`, so the generator can keep every input within the SPEC limits: at most 10,000 initial lines, 100,000 commands and 2,000 cursors, a document of at most 1,000,000 characters, inputs under 2 MB and print output under about 3 MB. Expected outputs come from `reference/main.py`. Run with `python3 run_tests.py textbuffer --tests-dir problems/textbuffer/bench -- <impl>/run.sh`.

The SPEC limits cap how heavy a single-cursor session can be, so `001` and `003` run near the limits on command count and input size. `002` is the heaviest input the limits allow.

- `001_editing_session_100k` is a 99,801-command single-cursor editing session on a 10,000-line code-like file. It mixes local and long-range `goto` navigation, arrow-key runs, word-by-word typing with frequent Enter-plus-indent, multi-line pastes of 3-12 lines, backspace runs, select-and-replace (including multi-line selections), and short undo/redo bursts. The document grows to about 800k characters and roughly 20k lines, and is printed three times (2 MB of output). This is the ordinary throughput case: parsing, line splitting and joining in a growing line array, undo bookkeeping and output formatting, with no single fast path dominating.
- `002_column_edits_2000_cursors` repeats a multi-cursor workflow 6,312 commands long. Each round places 500-2,000 cursors (mostly 2,000) at strides of 2-5 lines through `add-cursor`. It then runs 150-400 short edit scripts that hit every cursor: comment/uncomment, append `;`, wrap with `()`, split lines with `\n` plus indentation, backspace and delete-forward, `move up`/`down`/`left` with `select`, and in-script undo/redo. Rounds end with an undo/redo walk and `clear-cursors`. Each edit is up to 2,000 replacements on a document that grows to 780k characters and about 40k lines. This is the algorithmically hardest part of the spec: shifting later cursors, line insertion at many points, normalization, and recording and replaying 2,000-replacement undo entries. The scripts are what a column-editing user actually does, not one repeated degenerate command.
- `003_mixed_long_lines_undo` is a 97,022-command mixed session on a 2,500-line file that contains three 150k-character lines (like minified or generated code). About 60% of activity edits inside the long lines: typing, backspace and short selections at random columns, each costing O(line length) for a string-per-line buffer. The rest is ordinary short-line editing (selections are kept away from the long lines so they survive), multi-cursor edits with 5-300 cursors, and undo/redo walks of up to 120 steps that rewind and replay long-line edits. It covers the spec's long-line workload and deep undo inside a realistic mix.

## Long tier

`python3 problems/textbuffer/bench/gen_bench.py --long` writes `../bench-long/` (about an hour; expected outputs from the reference, peak reference RSS 1.8 GB on `002`). SPEC.md limits were raised for it: at most 1,000,000 commands, initial lines up to 3,000,000 characters, a document of at most 12,000,000 characters, an undo stack of up to 1,000,000 entries, and inputs and print output up to about 30 MB.

- `001_editing_session_100k`: the same session at 989,807 commands (10x). **Below the 5 s target**: single-cursor commands cost about 0.35 µs each, so 5-7 s would need about 20M commands (about 300 MB of input) and the undo history alone would need several GB. Measured 0.70 s wall (Go), 171 MB RSS.
- `002_column_edits_2000_cursors`: 360,648 commands (57x) of the same column-editing rounds; 95% of rounds now end by undoing every edit of the round (an abandoned experiment), which keeps the undo history and document bounded. Measured 26.1 s wall / 8.8 s user (D), 686 MB RSS (Go).
- `003_mixed_long_lines_undo`: 617,142 commands (6x) on a file whose three long lines are 3,000,000 characters each (was 150,000), so every long-line edit moves about 20x more text. Measured 18.0 s wall / 6.2 s user (Go; D 6.7 s user), 123 MB RSS.

Times are best of two on a heavily loaded machine (wall time was 2-3x user time). bench-long is about 49 MB.

With the canonical builds of all five languages: fastest 001 1.1 s (Go; still below target), 002 12.1 s (C++), 003 8.5 s (Go). Peak RSS is 1.49 GB (Go, 002). The Python implementation passes all three: 6.5 s, 560 s (1.19 GB) and 32 s.
