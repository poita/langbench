Build a standalone Haskell project that implements the specification in <root>/problems/bigint/SPEC.md, using the design in <root>/problems/bigint/APPROACH.md. <root>/CONVENTIONS.md describes the command-line contract and the build.sh and run.sh scripts the project needs.

Put the project in <root>/bigint/. Structure it the way a well-maintained open-source Haskell project of this kind would be:
- a reusable library with a clear, documented public API, split into modules by responsibility;
- a thin command-line tool on top of the library that implements the I/O contract in SPEC.md;
- the language's standard build tool and project manifest;
- a README.md: what it is, how to build it, how to use the CLI, and an example of using the library;
- automated tests, written the way the language's projects usually are.

Use GHC 9.14.1 and cabal 3.18.2.0; build it with cabal build; GHC's bundled packages are installed, and for tests hspec, tasty and QuickCheck, which cabal finds offline once they are in build-depends. Keep the build tool's standard optimisation settings. Use only the standard library, apart from a test framework for the tests. Don't use anything that implements the core of the problem for you; SPEC.md says what that rules out.

It's done when `cd <root> && bigint/build.sh && python3 run_tests.py bigint -- bigint/run.sh` passes every test (-v and --filter help with debugging) and the project's own tests pass. Scratch files can go in <root>/scratch/. If you think the spec or a test is wrong, say so.
