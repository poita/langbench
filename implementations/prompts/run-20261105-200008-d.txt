Build a standalone D project that implements the specification in <root>/problems/fulltext/SPEC.md, using the design in <root>/problems/fulltext/APPROACH.md. <root>/CONVENTIONS.md describes the command-line contract and the build.sh and run.sh scripts the project needs.

Put the project in <root>/fulltext/. Structure it the way a well-maintained open-source D project of this kind would be:
- a reusable library with a clear, documented public API, split into modules by responsibility;
- a thin command-line tool on top of the library that implements the I/O contract in SPEC.md;
- the language's standard build tool and project manifest;
- a README.md: what it is, how to build it, how to use the CLI, and an example of using the library;
- unit tests for the library, in files separate from the library source.

Use LDC 1.41.0 and dub 1.40.0; build it with dub build -b release --compiler=ldc2, and pass the same --compiler to dub test. Use only the standard library. Don't use anything that implements the core of the problem for you; SPEC.md says what that rules out.

It's done when `cd <root> && fulltext/build.sh && python3 run_tests.py fulltext -- fulltext/run.sh` passes every test (-v and --filter help with debugging) and the unit tests pass. Scratch files can go in <root>/scratch/. If you think the spec or a test is wrong, say so.
