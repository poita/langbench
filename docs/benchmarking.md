# Benchmarking

`lbench` builds a set of the implementations, runs each problem's benchmark
inputs, checks every output, and saves the results under a tag. Each problem
has three realistic workloads in two tiers, generated by its
`bench/gen_bench.py` and not stored in git:

- **long** (`bench-long/`, `make bench-long`): each input takes at least 5 s for
  the fastest implementation, so start-up and timer resolution are negligible.
  Language comparisons and published results use this tier.
- **short** (`bench/`, `make bench`, about 30 minutes): the same workloads at
  a fraction of the size, for quick iteration loops.

Suites choose a tier (`fast` short; `quick` and `all` long); `lbench run --tier` overrides it. It needs only
Python 3. Instruction and cycle counts come from `/usr/bin/time -l` on macOS
and from `perf stat` on Linux (install `perf` and allow user-space counting,
for example `kernel.perf_event_paranoid=2`); wall time, CPU time and peak memory
work everywhere.

Every build also records compile wall time and the compiler's own instructions
(through `CXX` and `RUSTC` wrappers, `go build -toolexec`, and the D compiler
each build script names). Go's standard library is compiled into the tag's
build cache first, so every language's builds compile only the project itself.

## Comparing languages

```
make bench-long                                     # once
./lbench build --tag langs --suite quick            # every language's canonical implementations
./lbench run   --tag langs
python3 tools/compare.py langs --baseline go        # cycles; --metric instr|wall|cpu|rss
```

## Comparing toolchains

`--toolchain LANG=PATH` builds one language with another toolchain: a C++
compiler (through `CXX`), `rustc` (`RUSTC`), a `go` binary, a Python
interpreter (also used at run time), or a D compiler. `--flags LANG=FLAGS`
adds compiler flags (`CXXFLAGS`, `RUSTFLAGS`, `GOFLAGS`, or appended to D
compiler invocations). Compare a change against a baseline:

```
./lbench build --tag base --langs rust && ./lbench run --tag base
./lbench ab --base base --tag try1 --toolchain rust=$HOME/rust/build/host/stage1/bin/rustc
./lbench ab --base base --tag try2 --flags rust="-C target-cpu=native"
```

`ab` builds and runs the new tag with the same suite and filters as the base,
then prints runtime and compile geometric means, per-problem ratios, the largest
regressions and improvements, and any change in correctness or build status.

Useful variations:

```
./lbench ab --base base --tag try3 --toolchain cpp=g++-15 --problems sat,toml   # a few problems
./lbench ab --base base --tag try4 --toolchain go=$HOME/go-dev/bin/go --metric cycles
./lbench compare base try1 --metric wall      # compare on wall time instead
./lbench list                                  # saved tags and their toolchains
./lbench show try1                             # per-problem numbers for one tag
```

## Suites

| Suite | Implementations | Use |
| --- | --- | --- |
| `fast` (default) | one per problem and language, first short input only, one run | The inner loop for toolchain work; narrow it with `--langs` |
| `quick` | one per problem and language, all three long inputs, warm-up plus three runs (one run past 15 s) | Language comparisons and published results |
| `all` | every canonical implementation, including repetitions, long inputs | Several code styles at once |

`--roots` replaces a suite's implementation set with every implementation under the
given directories, for example a newly generated run.

## Metrics and noise

Measured for D only so far, on an earlier set of agent-written D programs, by
running the same DMD build twice, and against LDC. Other
languages' noise has not been measured yet:

| Metric | `--metric` | Run-to-run noise (median, 90th percentile) | LDC vs DMD |
| --- | --- | --- | --- |
| Instructions retired (`lbench compare` default) | `instr` | 0.08%, 0.37% | 0.71x |
| Cycles | `cycles` | 1.9%, 5.7% | 0.74x |
| CPU time | `cpu` | 4.7%, 13.6% | 0.75x |
| Wall time | `wall` | 9.2%, 29.3% | 0.88x |

- Use **instructions** to tell whether a change did anything: differences of a
  few tenths of a percent are real. Programs whose garbage collector's work
  depends on address-space layout can vary more (D's kvstore: up to 4% between
  identical runs).
- Use **cycles** to judge how much a change matters: instruction counts ignore
  how efficiently instructions execute and overstate code-generation gaps.
- **Wall time** in `fast` carries process start-up and I/O on short inputs and
  is noisy with a single run; use `quick` (warm-up plus three runs) for wall
  time, and treat changes under about 3 percent there as noise.
- On macOS, instruction and cycle counts cover the measured process only. For
  runs that is the program itself (every `run.sh` execs it). For builds,
  `lbench` routes each compiler through a counting wrapper, so compile
  instructions are the compilers' own, summed over their invocations; build
  drivers (CMake, cargo, dub) are excluded, and clang is run with
  `-fintegrated-cc1` so its compile stage is counted. On Linux `perf stat`
  also counts child processes.
- Peak memory (`--metric rss`) is recorded too.

Each tag records every chosen toolchain's path, version line and git revision
(with `-dirty` when its tree has uncommitted changes), the default toolchains
used otherwise, the machine and the load average, so results stay
interpretable later. Builds happen out of tree
in `.lbench/builds/`; the repository is never modified. All state lives in
`.lbench/` (ignored by git); set `LBENCH_DIR` to keep it elsewhere.
